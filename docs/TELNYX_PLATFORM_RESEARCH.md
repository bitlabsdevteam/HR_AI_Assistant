## 1. Scope and evidence standard

This research surveys **every top-level product section in Telnyx's current public documentation index**: Fundamentals, Agent SDK, Agent Control Plane, Agent Tools, AI, Voice, Compute, Storage, Calling, Messaging, Numbers, and Wireless. It also covers Programmable Fax from the supporting API catalog. The challenge's Voice AI, inference, workflow, webhook, MCP, and Edge Compute dependencies receive additional technical scrutiny in the TDD. This is an understanding of the documented public platform, not a claim to know Telnyx's private implementation or to have tested every product.

The evidence comes from Telnyx developer documentation, its machine-readable public product catalogs, and the published `@telnyx/opencode` package README and metadata. Product pages establish documented behavior; catalog entries establish product scope, not successful execution. No account was authenticated, no number purchased, no call placed, no deployment created, and no tenant-specific entitlement, limit, or model availability verified during this research.

When sources differ, use the selected product's detailed contract and current schema over general marketing wording or illustrative challenge examples. The documentation itself distinguishes product behavior from contractual commitments. Prices, model inventories, account restrictions, beta availability, and runtime limits must be checked again during implementation.

Primary discovery sources: [root documentation index](https://developers.telnyx.com/llms.txt), [API authentication](https://developers.telnyx.com/docs/development/api-fundamentals/authentication.md), [official OpenAPI specification](https://raw.githubusercontent.com/team-telnyx/openapi/master/openapi/spec3.json), and [published OpenCode package](https://registry.npmjs.org/@telnyx%2fopencode).

## 2. Platform model

Telnyx combines a carrier network, programmable communications, GPU inference, and edge application infrastructure. Its public Voice overview describes a private global IP network with more than 20 points of presence, and its root index describes Telnyx-owned carrier infrastructure and GPU hosting. These descriptions explain the platform's integration model; they do **not** mean that every selectable speech or LLM provider runs on Telnyx infrastructure. Detailed provider documentation explicitly identifies third-party processing. [Voice overview](https://developers.telnyx.com/docs/voice/overview.md), [platform index](https://developers.telnyx.com/llms.txt), [AI processing and providers](https://developers.telnyx.com/docs/inference/data-residency.md).

The main boundaries are:

1. **Account and control plane:** Mission Control Portal, organizations, API credentials, billing, account levels, configuration, phone number resources, and product APIs.
2. **Communications and media:** PSTN/SIP calling, call control, TeXML instructions, WebRTC clients, messaging, and fax. Calls and messages have asynchronous lifecycle events.
3. **AI processing:** hosted or integrated LLMs, STT, TTS, assistants, workflows, retrieval, and agent tooling. Model and provider selection changes latency, cost, data handling, and availability.
4. **Application compute and persistence:** Edge Functions, Stateful Actors, KV, SQL, object storage, and network attachments. These are separate primitives with distinct state and consistency behavior.
5. **External application boundary:** custom tools, webhooks, MCP services, customer APIs, and storage destinations. Telnyx configuration does not automatically secure or govern these external systems.

These boundaries are synthesized from the official [calling](https://developers.telnyx.com/public/llms/calling.txt), [AI](https://developers.telnyx.com/public/llms/ai.txt), [compute](https://developers.telnyx.com/public/llms/compute.txt), [storage](https://developers.telnyx.com/public/llms/storage.txt), and [fundamentals](https://developers.telnyx.com/public/llms/fundamentals.txt) catalogs.

## 4. Cross-cutting contracts that matter to this challenge

### 4.1 Authentication, trust, and secrets

Server REST calls use `Authorization: Bearer <TELNYX_API_KEY>`. Keys are server-side secrets; Telnyx explicitly advises separate development/staging/production credentials and staged rotation. The REST key, webhook verification public key, SIP credentials, WebRTC client token, and a custom MCP credential have different purposes. Possession of a telephone number or caller ID is not application authorization; sensitive access needs an explicit application trust mechanism. [Authentication](https://developers.telnyx.com/docs/development/api-fundamentals/authentication.md), [Verify](https://developers.telnyx.com/docs/identity/verify.md).

Telnyx's Cloud Storage protocol is a notable compatibility exception. Its authentication page states that the API key is carried as the S3 `access-key-id`; the remaining signature components are ignored by that documented implementation. “S3 compatible” therefore does not imply AWS IAM or AWS signing semantics. The bucket binding avoids embedding S3 credentials in function code. Evaluate the selected storage operation's exact contract before using signed URLs or claiming AWS-equivalent security. [Storage authentication](https://developers.telnyx.com/docs/cloud-storage/authentication.md), [Object Storage overview](https://developers.telnyx.com/docs/cloud-storage/overview.md).

### 4.2 Webhooks and retries

For products that document Ed25519 signing, preserve the exact raw body and `telnyx-timestamp` / `telnyx-signature-ed25519` headers and verify against the account public key before trusting the event. Enforce an application replay window. Parsing and reserializing first invalidates raw-byte verification. Product contracts govern acknowledgment, retry/failover schedules, and event envelopes; there is no single universal webhook contract. [Webhook fundamentals](https://developers.telnyx.com/docs/development/api-fundamentals/webhooks/receiving-webhooks.md).

Ordinary notifications can be duplicated, concurrent, delayed, or out of order. Durable acceptance and idempotent processing are required. A synchronous instruction or variable callback is different: the response body is part of the protocol, so an “acknowledge and process later” notification design cannot simply be reused. The detailed dynamic-variable response deadline and signing contract must come from its own documentation. [Webhook fundamentals](https://developers.telnyx.com/docs/development/api-fundamentals/webhooks/receiving-webhooks.md), [TeXML fundamentals](https://developers.telnyx.com/docs/voice/programmable-voice/texml-fundamentals.md).

A timeout does not prove a mutation failed. Telnyx recommends bounded backoff/jitter and operation-specific idempotency; it explicitly warns against inventing an unsupported idempotency header. Mutations such as dialing, messaging, or purchasing require state reconciliation when the result is unknown. SDK and application retries must share a bounded total budget. [Retry contract](https://developers.telnyx.com/docs/development/api-fundamentals/reliability/command-retries.md).

### 4.3 Region, provider, retention, and recording are independent

* A regional API hostname steers processing under normal conditions but may fail over elsewhere. It does not change stored data location. Account Data Locality is a separate, one-time irreversible setting for covered records. [Regional endpoints](https://developers.telnyx.com/docs/account-setup/regional-endpoints.md).
* Inference offers per-request `region` plus `mode: "strict"` for supported Telnyx-hosted models with the matching ingress hostname. Unsupported/unavailable strict routing fails rather than silently moving. This is not a blanket guarantee over authentication, billing, logging, carrier transport, or external endpoints. [AI data residency](https://developers.telnyx.com/docs/inference/data-residency.md).
* Voice Assistant anchorsite is a preference by default. `privacy_settings.in_transit_data_locality` can require covered AI processing in the account's region, with constraints on models, speech providers, and ingress/media anchoring. Customer-supplied URLs are outside that guarantee. [AI data residency](https://developers.telnyx.com/docs/inference/data-residency.md).
* Telnyx hosts some STT/TTS/LLM options and integrates others. For example, the detailed matrix lists Deepgram Nova/Flux as self-hosted, Azure/Google STT as third-party, Telnyx TTS as self-hosted, and ElevenLabs TTS as third-party. Confirm the exact selected model rather than relying on the provider's brand alone. [Provider matrix](https://developers.telnyx.com/docs/inference/data-residency.md).
* `privacy_settings.data_retention` is enabled by default. Disabling it stops persisted conversation content and insights, but required billing/security/fraud records and timing metrics remain. Recording is controlled separately. [Retention](https://developers.telnyx.com/docs/inference/data-residency.md#data-retention-and-model-training).
* `privacy_settings.pii_redaction` defaults to `disabled`; `redact` changes stored history, tool arguments, and applicable stored webhook-tool responses. It does **not** redact live tool/webhook payloads, live conversation-ended deliveries, or audio recordings. Detection is heuristic. Webhook-tool response logs can remain even with conversation retention disabled. Application logging must enforce its own data minimization. [PII and retention details](https://developers.telnyx.com/docs/inference/data-residency.md#data-retention-and-model-training).
* The documentation says training/evaluation rights and opt-outs depend on the governing agreement/DPA; a blanket “never used for training” claim is not established by this research. [AI data handling FAQ](https://developers.telnyx.com/docs/inference/data-residency.md).

### 4.4 Limits, reliability, and cost

Rate limits vary by operation and region. Where supplied, inspect `x-ratelimit-*` and `retry-after`; even reset-header interpretation can be product-specific. A missing rate header does not imply unlimited capacity. Account framework and verification level are also tenant-specific. [Rate limiting](https://developers.telnyx.com/docs/development/api-fundamentals/reliability/rate-limiting.md), [Account levels](https://developers.telnyx.com/docs/account-setup/levels-and-capabilities.md).

The public SLA JSON describes **99.99% for core voice and messaging**, not a guarantee for the entire Assistant → tool → Edge → storage chain or for every beta product. It lists exclusions and credit tiers. End-to-end application targets need their own measurements. The root index exposes the platform status page, incident feeds, and component status APIs; application dependency and synthetic-call monitoring are still necessary. [SLA data](https://telnyx.com/ai/sla.json), [reliability resources](https://developers.telnyx.com/llms.txt).

Costs use different units: phone-number recurring fees, telephony minutes, Voice AI engine minutes, inference tokens, optional voice features, messages/segments and carrier fees, storage, and compute operations. The developer pricing page's representative Voice AI rate is a voice-engine charge with LLM tokens and telephony billed separately; it is not an all-inclusive call price. Those examples were checked by the publisher on 2026-09-16 and are not a tenant quote. Trial credit is not a nonbillable sandbox. [Pricing and billing units](https://developers.telnyx.com/pricing.md).

## 5. Telnyx Inference through OpenCode

The published `@telnyx/opencode` metadata identified **0.1.5** as `latest` when retrieved. Its repository is `team-telnyx/ai`, directory `plugins/opencode`. The package README verifies the challenge's installation and login commands:

```bash
opencode plugin @telnyx/opencode
opencode auth login --provider telnyx --method "API Key"
opencode auth list
```

Source: [npm registry package metadata and README](https://registry.npmjs.org/@telnyx%2fopencode), [official plugin repository](https://github.com/team-telnyx/ai/tree/main/plugins/opencode).

Documented behavior:

* Installation configures both the server plugin in `opencode.json` and the TUI plugin in `tui.json`. Manual server-only configuration can leave `/telnyx` unavailable.
* Authentication precedence is `TELNYX_API_KEY`, then the stored Telnyx credential in OpenCode's auth store. A stale environment variable can therefore override a valid stored key.
* Startup reads `GET https://api.telnyx.com/v2/ai/models`, filters for Telnyx-hosted text models, and applies the persisted allowlist at `~/.config/opencode/telnyx-models.json` (or the configured override).
* `/telnyx` manages enabled models; listing a model in some other Telnyx API does not prove it is hosted or enabled in this plugin.
* The package strips `maxOutputTokens` because its documented compatibility workaround addresses Telnyx's tool requests combined with `max_completion_tokens` / `max_tokens`.
* Thinking variants are registered only for the plugin's supported reasoning-model set; sending a reasoning flag to another model can fail.
* The plugin does not provision external-provider `api_key_ref` integrations. Using an external-provider model is not equivalent to the challenge's Telnyx-hosted coding requirement.

All bullets above are from the [published package README](https://registry.npmjs.org/@telnyx%2fopencode).

The 0.1.5 README recommends `moonshotai/Kimi-K2.6`, `zai-org/GLM-5.2`, `zai-org/GLM-5.1-FP8`, `MiniMaxAI/MiniMax-M3-MXFP8`, and `MiniMaxAI/MiniMax-M2.7`. The challenge illustrates Kimi-K3, GLM-5.3, and other families, while the current inference quickstart illustrates `zai-org/GLM-5.3-Flash`. These are different sources with different update cycles; they do **not** establish that any unlisted model is unavailable. Resolve the actual model through `/telnyx` and an authenticated current catalog, then record the chosen model ID and plugin version. [Challenge](../80639ad328bdbbcf732cba72559c894a/code_challenge.md), [package README](https://registry.npmjs.org/@telnyx%2fopencode), [Inference quickstart](https://developers.telnyx.com/docs/inference/getting-started.md).

This research and the requested planning documents are not evidence that the solution has already been built using OpenCode. The implementation phase must preserve truthful provenance: configuration, selected hosted models, session/build evidence, and a development log.

## 7. Source maintenance

Before coding, recheck the selected runtime/SDK versions, the Assistants API schema, workflow and dynamic-variable pages, MCP transport/auth compatibility, the actor/KV contracts, and the live hosted model catalog. Before public acceptance testing, recheck account limits, phone-number activation, deployed URLs, privacy settings, billable-unit pricing, and the operational alert path. These are validation needs, not claims that verification has already passed.
