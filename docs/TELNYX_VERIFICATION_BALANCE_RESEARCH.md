# Verification succeeds but leave balance is not queried

Research date: **2026-11-14**. Scope: the documented Telnyx MCP/voice-workflow contracts relevant to N10. Official pages below were fetched over HTTPS on this date. This documentation pass made no account changes, calls or deployments. The subsequent account investigation and local reproduction are recorded in the [incident report](incidents/2026-11-14-verification-balance-token-handoff.md); the discussion below distinguishes documentation facts from what documentation alone can prove.

## Finding to test first

The strongest compatibility concern is the result handed from `verify_employee` to the voice model. At the start of this investigation, [`src/tools.ts`](../hr-leave-assistant/src/tools.ts) returned the greeting alone in `content[].text`, with `auth_token` only in `structuredContent.data`. Its `get_leave_balance` input required `auth_token`. This is a source-code observation, not proof that Telnyx discarded structured content.

The current MCP specification says: **“For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block.”** The same advice is present in the 2025-06-18 specification. [1][2] The Telnyx assistant, workflow, MCP integration, and async-tool pages reviewed do **not** document whether `structuredContent` is forwarded into the voice model's context. [3][4][5][6]

Consequently, a client that exposes only the result's text would receive a successful greeting but no token to pass to the balance tool. Returning the complete small `ToolResult` envelope as a text block as well as structured content is a protocol-supported compatibility fix to test. It does not prove this was the affected call's cause, and it does not replace signature, expiry, or conversation-binding checks. The token belongs in the tool result needed by the model under the existing TDD design; it must never be spoken or copied into logs, research notes, or evidence files. [1][11]

The same compatibility rule matters for failures and balances: a text-only consumer needs machine-readable `ok`, error `code`, and fields needed by subsequent tools, not just a friendly sentence. The current spec distinguishes `structuredContent` from LLM schema-constrained generation; providing it does not itself guarantee an LLM sees it. [1]

## Dynamic variables are not an implicit MCP token handoff

The dynamic-variables guide describes substitution when the conversation starts, with values coming from API injection, SIP headers, the initialization webhook, or assistant defaults. Voice invokes that webhook at call start, whereas SMS/chat invoke it each turn. These are documented sources of variables; an arbitrary MCP result is not described as one. [9]

The API does document two explicit mechanisms for changing values during a call: a webhook tool's `store_fields_as_variables` response mappings, and an `update_dynamic_variables` tool with a declared `updatable_variables` allowlist. The former is a **webhook** configuration field; the latter is an additional model-called tool. Neither documents automatic assignment from `structuredContent.data.auth_token` on an MCP result. [7] Adding a placeholder such as `{{auth_token}}` to the existing prompt therefore has no documented basis for fixing the current MCP chain by itself.

Per-caller encrypted credentials are a separate feature. They populate the MCP server's `api_key_ref` (or a webhook header) from `encrypted_dynamic_variables`. Decrypted credentials are never visible to the model. On voice they are resolved at call setup and stay fixed until assistant handoff; a resolution failure excludes that MCP server for the call. They are not a documented method of capturing a token issued later by `verify_employee`, and MCP_SERVER_SPEC §11 excludes them from this implementation. [10][11]

## HTTP transport: valid shape, separate question

Telnyx's integration guide offers **HTTP** and **SSE** transport choices and expects the MCP endpoint itself as the URL. The Portal play button starts the connection and discovers tools without a conversation; Telnyx explicitly warns that discovery success does not prove task execution. [3]

The Streamable HTTP specification permits a JSON response to an MCP request; SSE is not mandatory. Clients send each JSON-RPC message as a new POST and advertise both `application/json` and `text/event-stream`. Accepted notifications receive `202` with no body; a server that does not offer a GET event stream may return `405`. Session IDs are optional; if issued, the client must return them. [12] This supports the project's stateless JSON transport design, but does not prove its deployed request/response headers or SDK behavior. A confirmed `verify_employee` completion over the same endpoint narrows investigation toward the result, next-call input, scope, or routing; it does not rule out an intermittent transport error on balance.

## Evidence that separates the hypotheses

Use an authorized synthetic call or a local synthetic reproduction. Preserve the project's log allowlist; never export caller speech or raw result/argument bodies into diagnostic artifacts. [11]

1. Establish whether verification **actually** completed with `outcome: verified`; a greeting alone is not that evidence. Then identify the next event for the same `conversation_id`/`call_ref`.
2. If **no balance request exists**, compare the model-visible result contract and effective allowed tools, then check whether a transition fired early. This is compatible with missing token visibility but does not prove it.
3. If balance returns **`unauthenticated`**, separate a missing/changed token from expiry, key change, and different/missing conversation binding. C-7 permits comparing token length and hash without logging its value. Equality should ideally be computed in memory and only the verdict retained. [11]
4. If balance returns **`invalid_input`**, inspect its input schema and which required field failed without logging the input. If it returns **`unavailable`/`error`**, investigate the balance handler/dependencies; successful verification does not prove balance execution succeeded.
5. A useful local compatibility check passes the verification result through a **text-only MCP client projection** and obtains the token from that text before calling balance with the same metadata. Also prove a modified/foreign token stays unauthenticated. This tests the suspected missing contract, without claiming it emulates Telnyx's undocumented projection.
6. Deployed acceptance remains C-7: the production voice model performs `verify_employee` → `get_leave_balance` in the same call, the returned balance is spoken, and the expected completion logs exist. Local tests and a Portal discovery check alone do not finish that slice. [11]

No reviewed official page guarantees byte-for-byte copying of arbitrary credentials by the model, explains the exact MCP-result-to-LLM projection, or establishes individual MCP-tool scoping on this account. The existing TDD's conversation-keyed actor-session fallback applies only if actual token relay remains unreliable after the compatibility issue is resolved; adopting that fallback is a separate design change, not a conclusion of this research. [11]
